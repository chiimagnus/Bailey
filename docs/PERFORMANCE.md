# 性能

本文供维护者定位打开文件、输入、滚动和 Git 操作的卡顿，负责优化优先级、测量口径和性能边界。相关执行路径、依赖或测量方式变化时同步更新；已解决的风险应删除或改为已验证的约束。
构建、安装与真机验收仍以[开发与验证](CONTRIBUTING.md)为准。

## 先减掉工作，不急着换引擎

当前最值得检查的是主线程上的读取与样式写入、每次编辑的全文访问、嵌入语言重复解析，以及 Git 刷新一次做了多少工作。后台执行能避免部分界面阻塞，但不会让重复计算、进程启动或 SSH 往返消失。

先测量，再优化最重的共享路径。没有证据表明需要把 SwiftUI、TextKit 或 WebKit 整体换成 Rust/Metal。

### 已有的优化

- 编辑器使用 STTextView/TextKit 2；Neon 按视口附近的范围请求高亮，Tree-sitter 保留根语言语法树做增量解析。
- 高亮查询按语言缓存；首次根语言高亮查询编译放在后台。编辑器字体和颜色的重复赋值已有守卫。
- 文件重载检查路径、代次和未保存状态；内容相同不会重建编辑器。
- diff 使用虚拟化的 `PierreMultiDiffView`；标签持有已创建的渲染视图，跨标签或项目重挂载时复用，首次选中时才创建。高亮有 worker 路径，历史 diff 不因重新选中而读取。
- Git 已改为事件驱动刷新，合并运行期间收到的请求，保留仓库快照；远程部分命令合并为批次。
- 文件与 Git 复用共享树模型和行，列表懒渲染；文件树不递归加载整棵目录。

不要重新实现这些能力。尤其不能把“每次重新选中 diff 都创建 WebView”或“所有文件都全文高亮”当成当前事实。

## 优先核查的路径

以下判断来自 2026-10-11 对 Kero 提交 `54985befa4f3f0c361d156dd03b92edf03435450` 及其锁定依赖的源码核对。它们是可定位的工作量和卡顿风险，不是 Instruments 已测出的耗时排名；本轮没有应用性能基线，也没有速度提升数据。
顺序用于安排首次测量，实际优化顺序服从 trace。

### 1. 首次打开文件：读取和解码仍在主线程

[文件标签](../kero/Editor/FileViewerView.swift)在主 actor 初始化时调用本地同步读取，再解码文本或创建图片。
[本地读取](../kero/Workspace/LocalWorkspaceBackend.swift)传入 `.max`；文本的 5 MiB 限制是在读完后检查。因此，最终显示“文件太大”的文件也可能先被完整读取。首次显示还会触发一次干净文件重载。

优先复用已有的异步 backend 和重载保护，让标签先可交互，再接收读取结果；同时把文本大小检查移到有界读取之前。图片预览的限制要单独决定，不能直接套文本上限，也不能把超限错误变成普通读取失败。

验证：首次与重复打开、超过上限、空文件、图片、慢磁盘/SSH，以及读取期间输入、保存、重命名和断线。旧结果不得覆盖新编辑。

### 2. 高亮：颜色更新夹带逐 token 的字体写入

[高亮桥接](../kero/Editor/SyntaxHighlightPlugin.swift)虽然使用空字体主题，却仍给每个 token 添加当前 `.font`；清理颜色时也写回字体。
[STTextView 的属性写入](../Vendor/STTextView/Sources/STTextViewAppKit/STTextView.swift)进入文本存储编辑事务，并标记需要布局。这不是单纯更新临时颜色，token 越多，事务和布局失效的工作越多。

优先测量并去掉无变化的字体写入，保留颜色的临时渲染属性。只有 trace 证明剩余样式更新仍过重，才考虑合并应用批次；不要为此重写整个文本组件。

验证：高密度 Swift/TSX、滚动、选区、字体切换、撤销，以及 Markdown 空范围。颜色正确不够，还要确认文本、字体、行号和撤销记录没有被样式更新破坏。

### 3. 输入：增量解析之外仍有全文访问和行号扫描

[编辑器同步](../kero/Editor/SourceTextEditor.swift)每次编辑获取 `textView.text`、比较新旧文本，再由 `FileTab` 对照保存基线判断是否未保存。[高亮桥接](../kero/Editor/SyntaxHighlightPlugin.swift)也获取全文，构造稳定的解析读取闭包。
但不能据此断言每次必然复制整篇文本：STTextView 的 getter 使用文本存储快速路径，实际桥接、比较和分配成本须测量。

更明确的风险是坐标转换：[锁定的 STTextKitPlus](https://github.com/krzyzanowskim/STTextKitPlus/blob/2ee74906f4d753458eeaa9a2f6d4538aacb86a1d/Sources/STTextKitPlus/NSTextContentManager.swift)的 `position` 枚举文档段落后查找所在行；编辑前后转换位置都会经过它。
[锁定的 Neon](https://github.com/kylemacomber/Neon/blob/ce8d252c8fd53ea0b6960e02c423315eef11f141/Sources/TreeSitterClient/TreeSitterClient.swift)还会在没有排队工作、编辑范围不超过 1024、文档长度不超过 1,000,000 时同步处理解析，不能认为所有解析都已离开主线程。

分别测量全文访问、脏状态比较、坐标转换和解析，再决定是否复用编辑增量、维护行起点索引或调整解析调度。后台解析必须读不可变快照，不能在后台读取正在变化的 AppKit 文本存储。单纯增加 `Task {}` 也不保证离开主 actor。

验证：在文件开头、中间和末尾编辑，连续输入、大粘贴、中文、emoji、CRLF、撤销回保存内容，以及解析尚未完成时再次编辑。撤销回原文仍须清除未保存标记。

### 4. Markdown/HTML 等嵌入语言：子区域反复从头解析

[嵌入语言路径](../kero/Editor/SyntaxHighlightPlugin.swift)收到根语言查询结果后，为返回的每个嵌入区域新建 `Parser`，解析整个片段并收集 token。查询编译有缓存，子区域解析结果没有；该工作在主线程回调里完成。
视口请求分段不等于嵌入片段也只处理可见部分，一个长代码块仍可能被重复处理。

优先按文档版本和区域身份复用子解析状态，并让耗时解析使用后台快照；颜色应用回主线程，版本不一致的结果丢弃。跨文档、跨语言不能误用旧缓存。

验证：长代码块、多个语言、滚动回同一区域、编辑或删除围栏、HTML 内脚本、未知语言，以及后台结果乱序到达。普通 TSX 的独立语法不能被普通 TypeScript 替代。

### 5. Git：一次状态刷新等待整套详情

[Git 快照](../kero/Git/GitStatusModel.swift)先取状态，还计算行数、读取未跟踪文件、查分支和远端、取带文件列表的提交历史、查储藏与仓库操作标记，最后一起发布。
未跟踪行数已有文件数和字节预算，远程已有批量查询；风险是这些次要数据仍延后主要状态出现。历史加载更多也扩大下一次完整快照的范围。

优先拆开状态与详情的失效条件：工作树或索引变了不等于提交历史、分支列表也变了。先让状态可用，再更新实际过期且需要显示的详情；相同结果不反复发布。先减命令和读取，再考虑有界并发，不能用无限并行 Git 进程补偿慢刷新。

验证：大量改动/未跟踪文件、初始提交前的仓库、加载更多历史、暂存/取消暂存、提交、切分支、冲突、两个项目快速切换和 SSH。操作开始前的旧快照不得覆盖操作后的状态，刷新期间的最后一个事件不能丢失。

### 6. diff：虚拟化和高亮 worker 没覆盖整条流水线

[diff 加载](../kero/Git/DiffViewerView.swift)通过 Git 检查 blob 大小再读取内容，部分步骤串行；工作区 diff 还读取文件和检查可编辑性。
[锁定的 Pierre 桥接](https://github.com/egoist-labs/PierreDiffsSwift/blob/3713d29360b750d3d6146b187ff3b77b7d498fee/Sources/PierreDiffsSwift/WebView/DiffWebViewCoordinator.swift)在主 actor 编码完整输入为 JSON 和 base64，再交给 WebKit 解码。
[JavaScript 入口](https://github.com/egoist-labs/PierreDiffsSwift/blob/3713d29360b750d3d6146b187ff3b77b7d498fee/scripts/src/diff-entry.js)同步构造内容版本和 `parseDiffFromFile`；worker 路径主要负责高亮，并不代表计算 diff、序列化和 DOM 更新全部在后台。worker 不可用时还有内联回退路径。

先分别测 Git、Swift 编码、WebKit 解码、diff 计算和首屏。相同输入已有比较守卫，不能把重复发布等同于必然完整重绘。确有变化时优先避免重复传输和重算，再判断是否需要依赖层的后台 diff 或批量 blob 读取。

验证：首次与重复选择、统一/并排切换、长行与大量变更、worker 回退、进入编辑模式、保存、Unicode，以及多 diff 标签跨项目切换。必须看到真实文本并能滚动/编辑，骨架或桥接 `ready` 消息不能单独证明完成。

### 7. 相邻路径：重复编译、文件树刷新与状态装饰

- 查询缓存只有已完成结果；同时首次打开同一语言的多个文件时，各 coordinator 仍可能重复编译。若冷启动 trace 命中，应合并正在进行的编译，而不是预编译所有语言。
- [文件树显示](../kero/Files/FileTreePanel.swift)由[工具面板](../kero/UI/Panels/ToolPanelView.swift)在前台可见时每两秒刷新，重新读取已展开目录。先测展开范围和远程往返；确有成本再缓存或定向失效，保留事件合并与最终刷新。
- `fileDecoration` 逐行查忽略前缀，目录状态还可能扫描改动集合。大树与大变更集叠加时，考虑在快照层预聚合目录状态；不得另建一套树行或关闭懒加载。

## 从 Zed 借什么

以下是 Zed 的公开设计和优化案例，不是 Kero 已实现的能力，也不是两款应用的性能对比测试。

| 做法与一手资料 | 对 Kero 的价值 |
| --- | --- |
| [Rope & SumTree](https://zed.dev/blog/zed-decoded-rope-sumtree)：分块文本、写时复制快照，按摘要定位文本坐标。 | 学习增量更新与便宜的稳定快照；先测全文桥接和坐标扫描，不立即造 Swift Rope。 |
| [Tree-sitter 低延迟编辑](https://zed.dev/blog/syntax-aware-editing)：增量更新根语言与嵌入语言树，后台更新时界面仍使用已有快照。 | 根语言已有增量能力，重点补齐子区域复用和版本保护，不重复引入解析器。 |
| [Git blame 卡死排查](https://zed.dev/blog/git-blame-beachball)：大量文件事件同时启动 Git，加上优先级反转，导致主线程等待。 | 合并失效、限制在途工作，并用线程状态查看等待；CPU 不高也可能严重卡顿。 |
| [Split diffs](https://zed.dev/blog/split-diffs)：早期持续测大变更集，减少初次构造和增量更新的无关工作，也发现共享布局与进程启动瓶颈。 | 优化真实流水线和共享路径，不只优化 diff 行；Zed 的进程 API 问题不能直接推定 Kero 的 `Process` 也有同一根因。 |
| [GPUI 的 120 FPS 排查](https://zed.dev/blog/120fps)：检查 CPU/GPU 同步、缓冲区生命周期，以及真实屏幕的显示节奏。 | 只有 trace 指向绘制和提交才查渲染层；GPU 加速不能消除主线程 I/O、全文比较或重复 Git。 |

## 测量口径

用同一台机器、同一构建配置和同一批公开或合成样本做前后比较。Debug 与优化构建分开记录，不把设备、刷新率或缓存差异算成优化收益。

### 分开记录用户看到的阶段

- **打开编辑器**：点击到可见文本、可输入、可见区域高亮稳定，分别计时。骨架不算文本首屏。
- **输入**：按键到文本/光标更新，以及高亮追上的时间；同时看主线程最长连续占用。
- **Git 面板**：状态可用、详情完成分别计时；记录 Git 进程数、读取量与 SSH 往返。
- **diff**：读取完成、桥接完成、真实首屏、可见高亮完成，以及滚动/编辑响应分别记录。
- **多标签**：冷开、重复切换、跨项目切换分别测；记录应用和相关 WebKit 子进程的内存，关闭标签后检查释放。
- **空闲**：前台、后台、面板隐藏分别看 CPU、唤醒和任务数量，避免用后台预热换取持续耗电。

[FPSCounter](../kero/Support/FPSCounter.swift)统计显示回调，不证明每次回调都提交了新内容，更不能代替输入延迟、GPU 帧时间或 WebKit 内部测量。

### 样本与重复

这是一组建议的起始样本，不是现有容量承诺或已经跑过的 benchmark：

- Swift、TSX、Markdown/HTML：约 32 KiB、512 KiB、4 MiB；包含高密度 token、长代码块和超长单行。
- 边界：空文件、中文/emoji、CRLF、二进制、图片，以及超过 5 MiB 的文本或 diff。
- Git：小仓库与上千改动文件，包含大量未跟踪文件、重命名、冲突和展开的提交历史；本地与 SSH 分开。
- 布局：单窗格、分屏、多个项目和多个已访问的 diff 标签；换行开/关、窄窗口和放大字体。

每组冷启动多次，说明如何清除进程内缓存；不为测量破坏用户文件或系统缓存。热操作至少重复 30 次，记录样本数、p50（中位数）、p95（95% 分位）和最差值。少量冷启动样本报告中位数与最差值，不包装成稳定的尾延迟结论。

### 工具与参考目标

先用 Instruments Time Profiler 定位 CPU 热点；卡顿但 CPU 不高时查看线程状态和等待。用 Allocations 检查文本快照、查询与 WebKit 视图的生命周期；WebKit 内的 diff 计算与 DOM 工作还需对应进程/网页性能工具，不能只看 Kero 主进程。
需要对齐阶段时，再在共享入口增加轻量 signpost（时间区间标记）；当前应用没有覆盖上述阶段的性能埋点和自动 benchmark。

[Apple 的响应性指南](https://developer.apple.com/documentation/xcode/improving-app-responsiveness)给出的粗略参考是：离散操作的同步主线程工作避免接近或超过 100 ms，连续交互要落在一次显示刷新内；60/120 Hz 分别约 16.7/8.3 ms，主线程更新最好更短。这些是调查目标，不是 Kero 已达成的数据或文件打开总耗时承诺。

## 什么算优化完成

每项改动记录：样本、硬件/系统/屏幕、构建配置与提交、冷/热状态、前后数据、定位到的热点，以及实际做过的正确性回归。没有测量就只记录实现变化，不宣称提速百分比。

不能为了性能移除以下边界：

- 保存失败保留编辑；异步读取、保存和解析结果不能覆盖更新的内容或错误的工作区。
- 字节、UTF-16、行列坐标保持一致；中文、emoji、CRLF 与空范围不能误着色或崩溃。
- Git 操作仍互斥，路径处理、超时、冲突与错误反馈不缩水；状态缓存按机器和仓库隔离。
- 文件与 Git 保持共享树行、懒加载、点击范围、键盘与无障碍行为。
- 缓存不能无限保留文档或视图；减掉计算后仍要检查内存和空闲开销。

改动的验收与安全替换应用流程见[开发与验证](CONTRIBUTING.md)。trace 可能包含文件内容、路径和终端输出，分享前脱敏，不把私人样本或原始 trace 默认提交到仓库。
